# Дизайн полноценного maintained fork для go-ts3

Дата: 2026-09-29

Статус: на проверке пользователем

## Контекст

`serezha93/go-ts3` уже является публичным GitHub-форком `rocketsciencegg/go-ts3`, который ранее находился по адресу `multiplay/go-ts3`. Upstream не архивирован, поэтому форк нельзя называть официальным преемником или утверждать, что upstream окончательно заброшен. При этом последний функциональный коммит upstream датирован февралем 2024 года, а открытые issues и pull requests обслуживаются нерегулярно.

Текущий форк нельзя использовать как самостоятельный Go-модуль без дополнительных настроек: `go.mod`, README, бейджи и документация всё ещё указывают на `github.com/multiplay/go-ts3`. CI слушает ветку `main`, хотя default branch называется `master`, поэтому push-проверки не запускаются. Существующий release workflow ориентирован на сборку бинарника, хотя проект является библиотекой.

## Цели

- Честно позиционировать проект как активно поддерживаемый community fork.
- Сохранить GitHub fork relationship, историю, лицензию и авторство upstream.
- Сделать форк устанавливаемым как `github.com/serezha93/go-ts3`.
- Ввести воспроизводимый quality gate для изменений и релизов.
- Выпустить первый maintained-релиз `v1.3.0`.
- Улучшить обнаруживаемость через GitHub metadata, профиль и pkg.go.dev.
- Подготовить доказуемо работающий проект до обращения к upstream за ссылкой.

## Нецели

- Не заявлять официальный статус или аффилированность с TeamSpeak.
- Не называть upstream abandoned без заявления его владельцев.
- Не отделять репозиторий от GitHub fork network.
- Не поддерживать одновременно два module path.
- Не добавлять новые продуктовые возможности в первый maintained-релиз.
- Не изменять ветки `update-crypto` и `pr-46`, связанные с upstream PR #46.
- Не включать Discussions и сложную governance до появления устойчивого потока пользователей.

## Module path и совместимость

`go.mod` меняется с `github.com/multiplay/go-ts3` на:

```text
github.com/serezha93/go-ts3
```

Все внутренние imports, примеры, команды установки, ссылки GoDoc и бейджи обновляются на новый путь. API намеренно сохраняется совместимым с `v1.2.0`; смена import path является единственным обязательным миграционным изменением первого релиза.

`MIGRATION.md` содержит:

- замену старого import path на новый;
- команду `go get github.com/serezha93/go-ts3@v1.3.0`;
- `go mod tidy` после изменения imports;
- примечание о сохранении API и исходной лицензии;
- способ сообщить о несовместимости.

Исторические теги `v1.0.0`–`v1.2.0` сохраняются как часть истории upstream. Первый тег maintained fork — `v1.3.0`. Тег создаётся только после прохождения всех локальных и GitHub-проверок; существующий тег никогда не перемещается.

## CI и release gate

Основной workflow запускается для pull requests и push в `master`. Проверки:

- `go build ./...` на Linux, macOS и Windows;
- `go test ./...` на Linux, macOS и Windows;
- `go test -race ./...` как минимум на Linux;
- `go vet ./...`;
- golangci-lint на Linux;
- проверка согласованности `go.mod` и `go.sum` после `go mod tidy`.

Версия Go берётся из `go.mod`, чтобы исключить расхождение локальной среды и CI. GitHub Actions обновляются до поддерживаемых major-версий. Dependabot еженедельно проверяет Go modules и Actions, группируя совместимые обновления.

Текущий GoReleaser workflow удаляется: библиотека не производит бинарный артефакт. Release workflow должен сначала повторить обязательные проверки, а затем создать GitHub Release из неизменяемого semver-тега с release notes и исходным кодом.

Защита `master` включает обязательный CI, запрет force-push и удаления ветки. Если GitHub не позволяет применить конкретное правило, это фиксируется как отдельный незакрытый operational gate; релиз до его решения не публикуется.

## Community и безопасность

Добавляются:

- `CONTRIBUTING.md` с локальными командами и правилами PR;
- `SECURITY.md` с поддерживаемой версией и приватным каналом сообщения;
- `docs/testing.md` с unit, race, vet, lint и release gates;
- формы issue для bug report и feature request;
- PR template с checklist тестов, совместимости и документации;
- Dependabot configuration.

Bug report запрашивает версию Go, версию TeamSpeak Server, транспорт ServerQuery, минимальный пример и фактическое поведение. Секреты, токены ServerQuery и адреса приватных серверов нельзя публиковать в issue.

## Порядок реализации и публикации

1. Создать отдельную рабочую ветку от `master`; не переиспользовать `update-crypto` или `pr-46`.
2. Исправить CI и добиться зелёного baseline до смены module path.
3. Изменить module path, README, migration и community-файлы.
4. Проверить локальные gates и установку из чистого временного Go-модуля.
5. Открыть PR в `serezha93/go-ts3` и дождаться GitHub-проверок.
6. Настроить repository description, topics, security settings и защиту `master`.
7. Слить PR в `master` и повторить проверки на итоговом commit SHA.
8. Создать неизменяемый тег `v1.3.0` и GitHub Release.
9. Проверить `go get github.com/serezha93/go-ts3@v1.3.0` в новой директории и доступность pkg.go.dev.
10. Закрепить репозиторий в профиле GitHub.
11. После доказуемо работающего релиза предложить upstream добавить нейтральную ссылку на maintained fork.

## Синхронизация с upstream

Upstream сохраняется отдельным remote. Новые upstream-коммиты просматриваются вручную и переносятся выборочно через обычный PR. Автоматический merge или force-sync запрещён: он может перезаписать развитие форка или нарушить новый module path.

Release notes разделяют изменения, полученные из upstream, и изменения maintained fork. Если upstream возобновит активную разработку, стратегия пересматривается отдельно; существующие теги и import path форка не меняются задним числом.

## Обработка ошибок и откат

- До публикации `v1.3.0` любое несовпадение module path, CI или документации исправляется в рабочей ветке.
- После публикации тег не перемещается; исправления выходят новым patch-релизом.
- При сбое release workflow релиз не создаётся повторно поверх существующего тега без проверки состояния GitHub Release.
- Repository metadata и branch rules изменяются только после успешного CI и проверяются чтением через GitHub API.
- Обращение к upstream не утверждает официальный статус и не требует перенаправления пользователей.

## Проверка результата

Работа считается завершённой, когда одновременно выполнены условия:

- GitHub явно показывает публичный community-maintained fork и корректный upstream;
- README, description и topics соответствуют позиционированию;
- все обязательные CI jobs проходят;
- `master` защищён от force-push и удаления;
- чистый Go-модуль успешно импортирует и тестирует `github.com/serezha93/go-ts3@v1.3.0`;
- pkg.go.dev отображает новый module path;
- GitHub Release `v1.3.0` связан с проверенным commit SHA;
- ветки `update-crypto` и `pr-46` не изменены;
- резервный путь восстановления — неизменяемая история Git и предыдущие теги — сохранён.
